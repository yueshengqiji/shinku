# 准入规则：哪些文件允许进入本仓库

**这份文件是 B 阶段的实际执行机制。** 没有它，"发布边界"只是文档里的一句话；
有了它，边界变成一条可检查的规则。

---

## 1. 一句话规则

> **只有 `INDEPENDENT_KEEP` 分类的文件可以进入本仓库。**
> 其余四种分类一律不进。

| 分类 | 允许进入？ | 理由 |
| --- | --- | --- |
| `INDEPENDENT_KEEP` | ✅ 可以 | 有独立来源依据 |
| `THIRD_PARTY` | ⚠️ 有条件 | 只能以**依赖声明**形式进入（`pyproject.toml`），且必须带许可证；不复制其源码 |
| `ARCHIVE_ONLY` | ❌ 不可以 | 本身就是"不入发布包"的分类 |
| `REWRITE_REQUIRED` | ❌ 不可以 | 未排除上游表达 |
| `UNCONFIRMED` | ❌ 不可以 | 证据不足；严格模式下与 `REWRITE_REQUIRED` 处理相同 |

分类定义与当前数量见旧项目的 `SOURCE_PROVENANCE.md`。

---

## 2. 为什么 B1 几乎什么都没搬

旧项目（`AkaneCompanionLab_Shinku`）当前 183 个运行时 Python 文件的分类分布：

| 分类 | 数量 | 说明 |
| --- | ---: | --- |
| `INDEPENDENT_KEEP` | **2** | `capability_adapters/__init__.py`、`local_workflow_runners/__init__.py`，依据是使用者的人工声明 |
| `UNCONFIRMED` | 36 | 与 Akane 字节完全相同；来源方向取证不足 |
| `REWRITE_REQUIRED` | 106 | 同路径但改过，来源未证 |
| （独有路径待核验） | 41 | 独有路径不等于原创 |

**那 2 个 `INDEPENDENT_KEEP` 文件也不能直接搬**——它们是旧包结构（`companion_v01/...`）下的
包标记文件，放进新包结构里没有意义；而且"可以进入"不等于"必须原样复制"。

所以 B1 的结论是：**新树从骨架开始，业务模块等 C 阶段逐个重写后进入。**
这不是保守过头，是这条规则算出来的唯一结果。

### 2.1 那 36 个 `UNCONFIRMED` 已经取证过了，为什么还是不能进？

2026-09-18 对这 36 个做了**三层来源对比**（内容同一性 / Git 归属 / 源码内部依赖），结论是：

| 等级 | 判据 | 数量 |
| :-: | --- | :-: |
| A | 不在 Akane 提交历史 + 源码依赖指向 Shinku 侧 | 9 |
| B | 不在 Akane 提交历史 + Shinku 侧有带日期的提交 | 14 |
| C | 不在 Akane 提交历史 + 仅落 Shinku 根基线内 / 两边都未提交 | 11 |
| D | 存在 Akane 侧提交历史 | 2 |

**34 / 36 在 Akane 的提交历史里完全不存在。** 这足以**证伪**「它们是 Akane 上游代码」。

**但仍然不能进入本仓库**，因为本规则第 1 条要的是 `INDEPENDENT_KEEP` —— 判据是
**「有独立来源依据 / 独立创作证据」**，而不是「已排除上游来源」。两者是不同的命题：

- 「不是从 Akane 来的」—— 取证已完成，答案是「否」；
- 「是使用者独立创作的」—— 仍未证，因为 Git 记录的是**在哪个仓库被提交**，不是**谁写的**。

所以这 34 个**仍记 `UNCONFIRMED`**，分级表作为证据附件挂在那里，
不改变发布门禁、不改变 C 阶段范围（142）。详见旧项目
`SOURCE_PROVENANCE.md` §5.7 与 `docs/shinku_independent_27_provenance_comparison_20260918.md` §7。

> **给未来维护者的提醒：** 如果哪天想把这 34 个直接放进发布包，
> 需要动的是**本规则第 1 条的判据定义**（或增设一个「排除了上游来源」的中间分类），
> 那是计划级改动，必须先明确改口径、再把已判 `REWRITE_REQUIRED` 的记录用同一标准重过一遍。
> 不要靠"证据看起来挺强"来绕过这一条。

## 3. 每个文件进入时必须回答的问题

搬运（或重写后加入）任何一个文件时，在 `docs/SOURCE_RECORD.md` 追加一行，写清：

| 字段 | 要求 |
| --- | --- |
| 路径 | 本仓库中的相对路径 |
| 进库日期 | YYYY-MM-DD |
| 来源 | 洁净室重写的批次号 + 行为契约文档路径 |
| 分类 | 上述五种之一（非 `INDEPENDENT_KEEP` 不允许进） |
| 与旧项目的关系 | 无 / 行为等价但独立实现 / 接口兼容 |
| 依据 | 哪份证据支持这个分类（重写记录 / 用户声明 / 许可证文件） |

## 4. 自动化检查（待补，记为 B 阶段欠账）

本规则目前靠**人工核对**。可以自动化的部分（尚未实现，明确记为欠账）：

- [ ] import graph 检查：本仓库不得出现指向旧项目包的导入；
- [ ] 文本扫描：本仓库不得出现旧项目独有的路径字符串、环境变量名（`COMPANION_*` 等）；
- [ ] 来源台账完整性：`docs/SOURCE_RECORD.md` 的行数应等于本仓库业务文件数；
- [ ] 依赖许可证清单：`pyproject.toml` 每个依赖都有对应许可证记录。

这四项归 D 阶段（依赖、素材与发布边界审计），因为其中三项依赖第三方许可证数据。
