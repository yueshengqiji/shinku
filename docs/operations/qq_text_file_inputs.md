# QQ 文本文件输入

## 行为与范围

群成员直接发送文本文件，或明确回复同一会话的文件消息时，聊天宿主可在本轮生成前读取附件正文。
文件引用不再被统一记成图片；文件名与 NapCat `file_id` 分开保留。

这是输入附件适配，不新增模型执行工具，不改变主人权限、审批、模型选择、发送开关或任务授权。
不被真红处理的被动观察消息只保存类型与引用，不触发文件下载。
宿主优先选择主消息及其明确引用；后续追问可通过同账号、同会话内的真实送达回复找回文件。
其他群、私聊或合并批次中其他人的文件不能自动成为来源。
文件正文只进入本轮 user context，不替换当前用户原话，不作为系统指令，也不自动写入长期记忆。

## 读取边界

- 通过 NapCat `get_file` 获取缓存描述，不使用消息自报的本机路径或 URL。
- 只读取显式配置的本账号缓存根或容器目录映射；默认没有文件缓存权限。
- 单文件上限 512 KiB，每轮最多两份；单份正文最多 12,000 字符。
- 入站大小未知、文件过大、类型不支持时，在平台缓存请求前拒绝。
- 支持 Markdown、TXT、JSON、CSV、常见配置及源码等文本扩展名，编码为 UTF-8 或带 BOM 的 UTF-16。
- PDF、Office、压缩包和其他二进制文件明确报告未支持，不假装已读取。
- 原文件全文已读、只读前缀及未取得正文分别标成 `read`、`partial`、`unavailable`。
- 保留字节哈希、大小、字符数和来源消息定位；不向模型交付平台凭据或缓存路径。
- 缓存读取逐层使用 `no-follow` 和目录描述符；拒绝目录穿越、符号链接和非普通文件。

平台接口依据：[NapCat 文件处理说明](https://napneko.github.io/develop/file)。
平台成功返回路径仍不代表正文可读，必须继续通过本账号映射、类型、大小及编码检查。

## 后续对话中的文件承接

文件读取后，宿主只将原消息定位、平台文件标识、来源作者、哈希及首次读取时间附到真实送达回复的 metadata。
这些描述复用现有消息库和送达记录，不创建另一套全局最近文件状态，也不保存文件全文。
引用回复的任意已送达分段，都可找回原件；再次生成时重新读取文件，并核对字节哈希。

- 直接提供或直接引用的新文件优先，不用旧上下文覆盖新上传。
- 回复链兼容最多四跳旧消息关系；新回复直接保存原件定位，不必每次遍历整段历史。
- 明确引用的来源记录保留最多 30 分钟的承接窗口；无引用时，只提供同一发言者首次读取后两分钟内的候选。
- 没有引用时，不自动借用其他群成员的文件；多份文件或多个版本只列候选并确认，不猜最新一份。
- 候选只说明本轮可参考的既有资料，提到修订版不等于平台已提供新版本。
- 每轮最多读取 64 个本会话已发送回复节点作定位；不存在按文件名扫描宿主缓存的回退。
- 旧记录缺少文件标识时，仅通过同一个原平台消息补齐；回取最多两次、每次最多五秒，账号、会话、作者和消息号均须一致。
- 原件被遗忘、过期、版本变化或平台不再返回时保留明确缺口，不把失败解释为用户从未提供文件。
- 发送前及逐段发送继续核对来源原件的版本和撤销状态，不让已经生成的正文绕过遗忘。

文件上下文的状态另含 `ambiguous`：已发现多份候选，但没有擅自选择或读取其中正文。
承接依赖现有记忆来源账本；该可选账本不可用时，本轮直接提供的附件读取仍可独立工作。

## 配置示例

以下路径为合成示例，实际部署应只映射对应 QQ 实例的接收缓存目录：

```dotenv
SHINKU_NAPCAT_FILE_PATH_MAPPINGS={"/container/cache/received":"/srv/napcat-cache/received"}
```

原生运行可用 `SHINKU_NAPCAT_FILE_ROOTS` 指定本账号缓存根。它与图片缓存配置相互独立。
不得为了读取单份附件，给出整个用户目录或其他账号的缓存权限。
